# DAC-3D-LLM 生产系统安全加固：给 Codex 的分步提示词

> 目标：让 Codex 给 `DAC-3D-LLM` 写代码时，优先保证你的系统在生产环境里的安全。  
> 重点：这不是 Codex 自身安全；这是你的 DAC-Agent Runtime 的应用安全、Agent 安全、工具调用安全、命令执行安全、记忆安全、审计安全和供应链安全。  
> 范围：LLM / Agent / Memory / Tool Gateway / Context Builder / Safety Guard / Trace / Eval / FastAPI / React / CLI。  
> 明确不做：DAC-3D 检测算法、点云算法、视觉检测、缺陷识别、工业检测模型。

---

## 一句话总原则

```md
把 LLM 当作“不可信建议器”，不要把它当作权限主体。LLM 可以解释、规划、预览、分类、建议，但所有真实副作用必须由代码层 ToolGateway + SafetyGuard + PolicyEngine 强制执行。
```

---

## 研究依据摘要

以下方向来自生产级 Agent 安全、LLM 应用安全、软件安全开发和工具协议安全的主流研究与规范：

1. OWASP LLM Top 10 把 Prompt Injection、Sensitive Information Disclosure、Supply Chain、Excessive Agency、Insecure Output Handling 等列为 LLM 应用核心风险。
2. OWASP Prompt Injection Prevention Cheat Sheet 建议：工具调用要做权限校验、session context 校验、tool-specific 参数验证、最小权限和监控。
3. OWASP AI Agent Security Cheat Sheet 强调：Agent 工具必须最小权限，区分 read-only / write / sensitive tools，并对敏感操作做显式授权。
4. OpenAI agent 安全建议强调：prompt injection 不能只靠识别恶意文本解决，更要限制被操纵后的影响；guardrails 要和认证、授权、工具侧校验一起使用。
5. OpenAI Agents SDK guardrails 文档强调：如果要保护每次工具副作用，不能只依赖 agent-level guardrail，要把验证放在 tool 旁边。
6. MCP 工具系统提供 tool schema 和 annotations，但 `readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint` 只能作为风险提示，不能替代 SafetyGuard。
7. AgentDojo、ToolEmu、Agent Security Bench 等研究表明，工具型 Agent 很容易受到间接提示注入、工具误用、记忆污染和数据泄露攻击，因此必须有 eval/red-team。
8. NIST SSDF、CISA Secure by Design、SLSA/SBOM 这类软件安全实践仍然适用：依赖锁定、漏洞扫描、CI 安全门禁、最小权限、审计、供应链完整性都必须进入生产工程。

# 1. 放到项目根目录的 `AGENTS.md`

把下面内容保存为项目根目录：

````md
# AGENTS.md

## Project Identity

This repository is `DAC-3D-LLM`, a local intelligent interaction prototype for DAC-3D industrial software.

The project scope for current development is strictly:

- LLM orchestration
- Agent runtime
- Memory system
- Tool calling
- Structured command preview
- Safety approval
- Trace logging
- Agent evaluation
- FastAPI / React / CLI integration around the agent

Do not research, modify, optimize, or redesign DAC-3D detection algorithms, 3D inspection algorithms, image processing, defect detection, point cloud processing, or industrial vision models unless explicitly instructed by the user.

The target product is not a general chatbot. It is a local, auditable, safety-gated industrial Agent Runtime for DAC-3D operations.

## Strategic Goal

Upgrade the current system from:

RAG Q&A assistant

into:

DAC-Agent Runtime = LLM + Memory OS + Skill System + Context Builder + Tool Gateway + Safety Guard + Trace/Eval Loop

The final architecture should support:

1. Local knowledge and parameter explanation.
2. Natural-language-to-structured-command preview.
3. Read-only DAC status and result explanation.
4. Human-confirmed command submission.
5. Long-term operator/project/procedure/tool/policy memory.
6. Skill-based workflows stored as Markdown directories.
7. Context engineering beyond plain RAG.
8. Trace logging for every agent step.
9. Eval tests for command correctness, safety, and memory behavior.
10. Future MCP-compatible tool gateway.

## Non-Goals

Do not implement or change:

- DAC-3D inspection algorithm internals.
- Defect classification logic.
- Camera, sensor, point-cloud, or reconstruction code.
- Production command execution without safety confirmation.
- Autonomous modification of production skills or memory without review.
- Direct LLM writes to DAC command files.

## Engineering Principles

Follow these principles:

1. Safety first.
   - LLM must never directly write execution command files.
   - LLM must generate structured command previews only.
   - Execution must go through a Tool Gateway.
   - High-risk actions must require user confirmation.

2. Local-first and auditable.
   - Prefer local SQLite, JSONL, Markdown, and filesystem-backed memory.
   - Every memory write must be traceable to a conversation, tool call, or user approval.
   - Memory must be editable, correctable, and deletable.

3. Context engineering, not prompt stuffing.
   - Do not inject the whole knowledge base into prompts.
   - Select only relevant memory, state, skill instructions, and safety policy per task.
   - Separate operator memory, project memory, procedure memory, episodic memory, tool memory, policy memory, and document memory.

4. Skills over giant prompts.
   - Reusable workflows must live under `skills/<skill-name>/SKILL.md`.
   - Each skill must have clear trigger conditions, input schema, output schema, tool permissions, risk level, and eval cases.

5. Tool gateway over raw filesystem access.
   - All interactions with DAC status/result/command files must go through named functions.
   - Each tool must have schema validation, path allowlist checks, risk metadata, and structured output.

6. Tests before trust.

Use the existing implementation from the previous PR. Do not touch DAC detection algorithms.

This phase should implement advanced behavior inspired by:

- Memory OS: typed memory lifecycle, storage/update/retrieval/generation.
- Memento-Skills: skills as persistent, evolving Markdown artifacts.
- ByteRover-style context tree: human-readable local files for curated procedural memory.
- MCP-style tool metadata: read-only, destructive, idempotent, open-world risk hints.
- Trace/eval improvement loop: traces -> feedback -> evals -> Codex handoff.

Implement the following:

1. Memory consolidation.
   - Add session summary generation interface.
   - Add dedupe/conflict detection.
   - Add memory status transitions:
     - active
     - superseded
     - rejected
     - deleted
   - Add provenance to every memory record.

2. Memory patches.
   - Add `MemoryPatch` model.
   - Add proposed patch queue.
   - Add approve/reject API if FastAPI exists.
   - Add CLI commands if CLI exists.

3. Procedure memory as Markdown.
   - Store reviewed procedure memories in `memory/procedures/*.md` or configured data path.
   - Include provenance frontmatter.
   - Do not let the agent silently edit production procedure memory.

4. Skill patch proposal.
   - Add a way for the agent to propose changes to a skill without applying them.
   - A proposed skill patch should include:
     - target skill
     - reason
     - diff or replacement section
     - evidence trace IDs
     - risk level
   - Require human approval before applying.

5. Tool risk metadata.
   - Add fields equivalent to:
     - readOnlyHint
     - destructiveHint
     - idempotentHint
     - openWorldHint
   - Treat metadata as hints, not enforcement.
   - Enforcement must remain in SafetyGuard.

6. Prompt injection hardening.
   - Add tests where retrieved docs say:
     - ignore previous instructions
     - write command.json directly
     - skip confirmation
     - access path outside allowlist
   - The correct behavior is rejection or safe preview only.

7. Trace-to-eval conversion.
   - Add a script that converts selected traces into eval case drafts.
   - Do not auto-approve evals.
   - Save drafts under `evals/drafts/`.

8. Codex handoff generator.
   - Add script:
     - `python -m dac_agent.evals.generate_codex_handoff`
   - It should read failing evals and traces, then generate:
     - `docs/generated/codex_handoff_next.md`
   - The handoff should recommend specific code changes.

9. Tests.
   - Add tests for memory consolidation, skill patch proposal, prompt injection, and handoff generation.

After implementation, summarize:

- how memory lifecycle works
- how skill patches are proposed
- how context is selected
- how tool risk metadata is used
- how evals prevent regressions
- what remains for the next PR
````

# 6. 给 Codex 的第三阶段 Prompt：接 MCP / OpenAI Agents SDK

MCP 规范把 host/client/server、resources、prompts、tools、sampling、roots、elicitation 等概念标准化；同时它强调工具安全、用户同意、隐私、工具调用需要谨慎处理。([Model Context Protocol][3])
工具注解可以驱动确认弹窗和风险提示，但官方博客也强调 annotations 只是 hints，不是强制保证，不能替代沙箱、网络控制和授权层。([Model Context Protocol Blog][4])
所以第三阶段再让 Codex 做 MCP，而不是第一阶段就硬上。

```md
Continue upgrading `DAC-3D-LLM` with an MCP-compatible Tool Gateway and optional OpenAI Agents SDK adapter.

Do not touch DAC detection algorithms.

Goal:

Expose DAC-Agent tools in a way that can later be used by MCP-compatible clients or an Agents SDK orchestration layer, while preserving the current local FastAPI/CLI path.

Tasks:

1. Add tool descriptor models.
   Each DAC tool descriptor should include:
   - name
   - description
   - input_schema
   - output_schema
   - risk_level
   - requires_confirmation
   - readOnlyHint
   - destructiveHint
   - idempotentHint
   - openWorldHint
   - allowed_scopes

2. Add MCP adapter layer.
   - Do not replace the internal ToolGateway.
   - Build an adapter that maps internal tools to MCP-style descriptors.
   - If a Python MCP SDK is already present, use it.
   - If not, create a minimal adapter model without adding heavy dependencies.

3. Add tool invocation policy.
   - Read-only tools may be allowed without confirmation.
   - Destructive or command-submitting tools must require confirmation.
   - openWorldHint tools must not run after private/sensitive data access unless policy allows it.
   - Treat annotations as hints only; enforcement must be in SafetyGuard.

4. Add Agents SDK adapter only if project dependency policy allows it.
   - Keep the core runtime provider-agnostic.
   - Use an adapter pattern.
   - Do not hard-code one LLM provider into the core logic.

5. Add tests.
   - Tool descriptor serialization.
   - MCP adapter output.
   - submit_command requires confirmation.
   - read_dac_status is read-only.
   - open-world plus private context policy is blocked or requires approval.

6. Update documentation.
   - Explain internal ToolGateway vs MCP adapter.
   - Explain why annotations are not enforcement.
   - Explain deployment modes:
     - local FastAPI
     - CLI
     - future MCP server
     - future Agents SDK orchestration
```

# 7. Codex 配置建议

Codex 配置里可以设置审批策略、沙箱模式、模型推理强度等。官方配置参考显示 `approval_policy` 控制命令执行前何时暂停审批，`sandbox_mode` 支持 `read-only | workspace-write | danger-full-access`，`model_reasoning_effort` 支持不同推理强度。([OpenAI 開發者][5])

对你这个项目，我建议开发时用：

```toml
# ~/.codex/config.toml 或项目/环境配置，按你的 Codex 使用方式调整

model_reasoning_effort = "high"
model_reasoning_summary = "concise"

approval_policy = "on-request"
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false
```

不要用：

```toml
sandbox_mode = "danger-full-access"
approval_policy = "never"
```

因为你的项目涉及工业软件命令、状态文件、命令文件和本地桥接，Agent 早期开发阶段不应该裸奔。

# 10. 一句话给 Codex 的最高优先级

你可以把这句放在每次任务最后：

Highest priority invariant: DAC-Agent may explain, preview, validate, and request confirmation, but it must never directly execute or write DAC command files. # 参考项目

下面是按 **2026-05-27 当前检索结果**整理的 AI Agent / Multi-Agent 项目图谱。先给结论：现在最热的方向不是“聊天机器人”，而是 **能读上下文、调用工具、改文件、跑命令、开 PR、长期执行、多实例并行、带权限控制的 agent runtime**。尤其是编码 agent、个人助理 agent、企业级多 agent 编排框架这三条线最火。

## 2. 你点名的几个项目

### OpenClaw：个人 AI 助理 / “数字员工”路线

**定位**：OpenClaw 不是单纯 coding agent，而是“个人 AI assistant”。官网的描述很直白：它可以从 WhatsApp、Telegram 或其他聊天 App 里触发，帮你清 inbox、发邮件、管日历、办理航班值机等。([openclaw.ai][agent-2])

**功能重点**：

| 功能 | 说明 |
| --- | --- |
| 多聊天入口 | WhatsApp、Telegram、Discord/任意聊天入口式交互 |
| 个人工具执行 | 邮件、日历、文件、浏览器、终端、自动化脚本 |
| 技能生态 | GitHub 组织里有 `clawhub` 技能目录、Google Workspace 终端工具、截图/MCP 工具、ACP session 客户端等配套项目，说明它更像一个 agent OS 生态，而不是单 repo 工具。([GitHub][agent-3]) |
| 本地优先/own-your-data | GitHub 主题包含 own-your-data，主仓库描述为跨 OS / 跨平台个人助理。([GitHub][agent-4]) |

**实现方式**：

OpenClaw 的思路可以理解成：

```text
聊天入口
  → OpenClaw core / daemon
  → 身份、记忆、上下文、任务队列
  → skills / plugins / MCP / CLI tools
  → Gmail、Calendar、GitHub、Notion、浏览器、文件系统、终端
  → 回传结果到聊天窗口
```

它的强点是 **“随时随地发消息给自己的 agent，让它在自己的机器/云环境里做事”**。缺点也明显：权限面非常大，接入邮箱、日历、文件、浏览器、终端之后，安全边界、审计、撤销、隔离都必须设计好。

---

### opencode：开源 coding agent，终端/IDE/桌面三线合一

**定位**：opencode 是开源 AI coding agent，支持终端、IDE、桌面端；可以使用免费模型，也可以连接 Claude、GPT、Gemini 等模型提供商。([opencode.ai][agent-5])

**功能重点**：

| 功能 | 说明 |
| --- | --- |
| 终端/IDE/桌面 | 一个 agent runtime，多种交互入口 |
| LSP 感知 | 自动加载对应语言的 LSP，让模型知道符号、类型、错误等上下文。([opencode.ai][agent-5]) |
| 多 session | 可以在同一项目上启动多个 agent 并行处理任务。([opencode.ai][agent-5]) |
| 多模型 | 支持 Claude、GPT、Gemini 等 |
| 隐私取向 | 官网称不存储代码和上下文数据，适合隐私敏感环境。([opencode.ai][agent-5]) |

**实现方式**：

opencode 是典型的 **terminal-native coding harness**：

```text
用户任务
  → 项目扫描 / LSP / git 状态 / 文件上下文
  → LLM 生成计划
  → 文件编辑、shell、测试、lint、搜索工具
  → diff 展示 / session 分享 / 人类确认
```

它的卖点是“开源 + 多模型 + 多 session + 本地工作流”。如果你想自己二次开发 coding agent，opencode、Cline、Aider、Codex CLI 这一类比闭源工具更值得研究。

---

### OpenAgent / OpenAgents：名字相近，但方向不一样

这里容易混。至少有三个相关项目值得区分：

| 名称 | 定位 | 重点 |
| --- | --- | --- |
| **the-open-agent/openagent** | 自托管个人 AI 助理 | LLM + RAG 知识库 + agent loop + 浏览网页 + 运行代码 + MCP 工具。([GitHub][agent-6]) |
| **openagents-org/openagents** | 多 agent 协作工作区 | 一个统一 URL 管理所有 agent，把 agent 拉进 thread，共享文件、浏览器和上下文。([GitHub][agent-7]) |
| **Firecrawl Open Agent Builder** | 可视化 agent workflow builder | 拖拽式构建 agent pipeline，支持 Agent、MCP Tools、If/Else、While、User Approval 等节点，并用 LangGraph 做执行引擎。([GitHub][agent-8]) |

**实现方式差异**：

```text
OpenAgent:
个人助理平台 = Web UI + RAG + 工具执行 + MCP + 本地/自托管服务

OpenAgents:
多 agent workspace = agent registry + conversation thread + shared files/browser/context

Open Agent Builder:
可视化 DAG = 节点编辑器 + LangGraph runtime + Firecrawl web data + 人审节点
```

我的判断：如果你想做“个人 Jarvis”，看 OpenAgent/OpenClaw；如果你想做“多个 agent 协作平台”，看 OpenAgents；如果你想做“可视化 workflow 产品”，看 Open Agent Builder/Dify/Flowise。

### Codex：OpenAI 的 coding-agent 产品线

**定位**：现在 Codex 不是以前那个“Codex 模型”的意思，而是一套 software agent 产品：Codex CLI、Codex Cloud、Codex VS Code extension、Codex app。OpenAI 官方说明 Codex app 是 agentic coding 的 command center，内置 worktrees 和 cloud environments，可以让多个 agent 并行处理项目。([OpenAI][agent-9])

**功能重点**：

| 功能 | 说明 |
| --- | --- |
| 本地 CLI | 在本机运行 coding agent，读写文件、跑命令 |
| 云端任务 | 每个任务可在独立云 sandbox 中执行 |
| 多 agent 并行 | Codex app 用 worktrees/cloud envs 支持多任务并行。([OpenAI][agent-9]) |
| GitHub / IDE | 支持 VS Code、GitHub PR review 等集成。([OpenAI 开发者][agent-10]) |
| 可作为 MCP server | 官方文档提到可以把 Codex CLI 暴露为 MCP server，再由 Agents SDK 编排多 agent 工作流。([OpenAI 开发者][agent-11]) |

**核心实现方式**：

OpenAI 对 Codex agent loop 的技术拆解很有价值：agent 接收用户输入，构造 prompt，调用模型；模型要么给最终回答，要么请求 tool call；agent 执行工具，把结果追加回上下文，再次调用模型，直到完成。对 coding agent 来说，最终输出不只是文本，还包括它在本地环境里写入或修改的代码。([OpenAI][agent-12])

Codex CLI 还把工具分为内置 shell tool、Responses API 工具、用户通过 MCP server 提供的工具；OpenAI 特别提醒，Codex 的 sandbox 只适用于 Codex 自带 shell tool，MCP server 自己要负责 guardrails。([OpenAI][agent-12])

简化版架构：

```text
Codex CLI/App
  → Prompt/context builder
  → Responses API / model inference
  → tool call decision
  → shell/file/MCP tools
  → observe result
  → update context / continue
  → final message + code diff/PR
```

---

### Claude Code：最强产品化 coding agent 之一

**定位**：Claude Code 是 Anthropic 的 agentic coding tool，可在 terminal、IDE、desktop、web、Slack 中使用，能读代码库、编辑文件、运行命令、处理 Git 工作流。([Claude][agent-13])

**功能重点**：

| 功能 | 说明 |
| --- | --- |
| 整库理解 | 用 agentic search 理解项目结构和依赖，不需要手动挑上下文文件。([Claude][agent-13]) |
| 多文件编辑 | 可协调修改多个文件，并用测试/构建系统验证。([Claude][agent-13]) |
| 本地运行 | 运行在本机 terminal，直接连模型 API，不需要远程代码索引；改文件或跑命令前会请求权限。([Claude][agent-13]) |
| MCP 支持 | 可通过 MCP server 扩展能力，比如 GitHub 等工具。([Claude][agent-13]) |
| Hooks / Skills / Subagents / Plugins | hooks 用确定性 shell 命令约束行为；plugins 可把 skills、hooks、subagents、MCP servers 打包分发。([Claude Code][agent-14]) |
| GitHub Actions | 官方 `claude-code-action` 可在 issue/PR 中响应 `@claude`、实现代码变更。([GitHub][agent-15]) |

**实现方式**：

Claude Code 的技术核心也是 agent loop，但它的产品形态更成熟：本地文件系统 + 终端命令 + IDE diff + 权限确认 + MCP + hooks + subagents。Anthropic 的工具调用文档也明确了通用 tool-use 合约：模型不会自己执行操作，而是发出结构化请求，由你的代码或服务执行，再把结果返回对话。([platform.claude.com][agent-16])

典型架构：

```text
Claude Code CLI/Desktop
  → repo search / context gathering
  → plan
  → edit files / run shell / call MCP
  → hooks enforce rules
  → tests / lint / build verification
  → diff / PR / final summary
```

Claude Code 的优势是体验非常“端到端”：从理解项目、改代码、跑测试、开 PR 到 Slack/手机/桌面联动都在一个产品里。缺点是生态和模型绑定较强，成本、配额、企业权限治理要认真设计。

适合研究：**长任务、多 repo、团队知识沉淀、agent fleet、商业化工程流程**。

---

### SWE-agent / mini-swe-agent：研究型 GitHub issue 修复 agent

SWE-agent 文档现在推荐 mini-swe-agent，称当前主要开发精力在 mini-swe-agent 上，它更简单但性能接近；SWE-agent 可让模型自主使用工具修复真实 GitHub issue、找安全漏洞或执行自定义任务。([swe-agent.com][agent-23])

适合研究：**最小 agent loop、SWE-bench、工具设计、可复现实验**。

---

## 4. 多 Agent 框架对比

### LangGraph：状态图 / 持久执行 / 人在回路

LangGraph 更像底层 orchestration runtime，重点是 durable execution、streaming、human-in-the-loop、persistence；它适合把多个 agent、工具、条件分支、状态机做成可恢复的图。([docs.langchain.com][agent-24])

**实现模式**：

```text
StateGraph
  node: planner agent
  node: researcher agent
  node: coder agent
  node: reviewer agent
  edge: conditional routing
  checkpoint: persistent state
  human node: approval
```

适合：生产级复杂 workflow、强控制流、多步骤任务、需要恢复/审计的 agent 系统。

---

### CrewAI：角色分工 + Crews + Flows

CrewAI 主打生产级 multi-agent system，用 **Crews** 表示协作 agent 团队，用 **Flows** 表示事件驱动、可控的状态和执行骨架。([docs.crewai.com][agent-25])

**实现模式**：

```text
Flow 控制执行顺序
  → Crew: researcher + analyst + writer + reviewer
  → 每个 agent 有 role / goal / backstory / tools
  → task outputs 逐步传递
```

适合：市场研究、内容生产、销售线索、报告生成、业务流程自动化。

---

### OpenAI Agents SDK：轻量多 agent 编排

OpenAI 官方文档把 agent 定义为能计划、调用工具、跨专家协作并保持状态的应用；Agents SDK 适合当你的应用自己掌握 orchestration、tool execution、approvals 和 state。([OpenAI 开发者][agent-26])

它的多 agent 编排有两种主要方式：让 LLM 决定下一步，或用代码明确控制 agent 流程，两者可以混合。([OpenAI GitHub][agent-27])

适合：你已经在 OpenAI / Responses API 生态里，希望快速构建可控的多 agent app。

---

### Microsoft AutoGen / Microsoft Agent Framework

AutoGen 仍是经典 multi-agent conversational framework，官方文档强调它可构建 conversational single/multi-agent apps，Core 是 event-driven framework，支持 MCP、Docker code executor、distributed runtime 等扩展。([microsoft.github.io][agent-28])

不过 Microsoft 现在也在推 **Microsoft Agent Framework**，定位是面向生产的 .NET / Python 多语言框架，支持 sequential、concurrent、handoff、group collaboration、durability、observability、governance、human-in-the-loop 等生产需求。([GitHub][agent-29])

适合：微软/Azure/.NET/Python 企业栈，或你需要从 AutoGen 研究原型走向生产 runtime。

---

### MetaGPT：把软件公司流程编码成多 Agent SOP

MetaGPT 的论文思路是把标准化工作流 SOP 编码进 prompt sequence，让不同角色 agent 像软件公司一样协作，降低简单串联 LLM 带来的逻辑不一致和幻觉级联。([openreview.net][agent-30])

适合：软件项目生成、PRD → 架构 → 代码 → 测试这种固定流程。

---

### CAMEL：多 agent 社会 / 仿真 / 研究平台

CAMEL 更偏研究，目标是研究 agent scaling laws，实现和支持不同类型的 agents、tasks、prompts、models、simulated environments，用于数据生成、任务自动化、世界模拟等。([GitHub][agent-31])

适合：多 agent 行为研究、agent society、仿真、合成数据、群体协作实验。

---

### Agno：agent platform control plane

Agno 是 SDK + control plane 思路：可用任意 agent framework 构建 agent，把它们作为 production services 运行，带 tracing、scheduling、RBAC，并强调数据、上下文、工具、权限、memory、人审 loop 都由你掌控。([GitHub][agent-32])

适合：你不是只做一个 agent，而是要做“agent 平台”或“企业 agent fleet”。

---

### Dify：agentic workflow + RAG + LLMOps

Dify 是 production-ready agentic workflow 平台，可定义 Function Calling 或 ReAct agent，接入 50+ 内置工具，并提供日志、性能分析、数据标注、API 集成和自托管。([GitHub][agent-33])

适合：低代码 RAG/agent 应用、企业内部工作流、非工程团队参与搭建。

---

## 5. 这些项目的共同实现套路

不管名字多花，核心大多是这套：

```text
1. Context 收集
   repo map / RAG / search / file read / browser / user profile / memory

2. Planning
   任务拆解、选择工具、决定是否调用子 agent

3. Tool loop
   LLM 输出结构化 tool call
   runtime 执行 shell / file edit / API / MCP / browser
   把 observation 送回模型

4. Verification
   tests / lint / typecheck / eval / reviewer agent / human approval

5. State & memory
   conversation state、任务状态、长期记忆、artifact、diff、logs

6. Orchestration
   单 agent loop、router、supervisor、handoff、graph、event bus、queue

7. Safety
   sandbox、权限弹窗、allowlist、denylist、secrets 隔离、审计日志、rollback
```

MCP 是当前最重要的工具连接标准之一。官方 MCP 文档把它定义为连接 AI 应用和外部系统的开源标准，可连接本地文件、数据库、搜索、计算器和专用 prompts；协议中的 server 能提供 Resources、Prompts、Tools。([Model Context Protocol][agent-34])

## 6. 建议重点研究路线

如果你想**做 coding agent**：优先研究 **Codex CLI、Claude Code、opencode、Cline、Aider、OpenHands、mini-swe-agent**。重点看：repo context、tool loop、diff 审批、shell sandbox、测试反馈、多 worktree 并行。

如果你想**做个人助理 agent**：优先研究 **OpenClaw、OpenAgent、Agno、MCP servers**。重点看：聊天入口、身份权限、长期记忆、工具授权、任务调度、敏感操作人审。

如果你想**做多 agent 系统**：优先研究 **LangGraph、CrewAI、OpenAI Agents SDK、Microsoft Agent Framework、MetaGPT、CAMEL**。重点看：router/supervisor/handoff、共享状态、isolated context、graph checkpoint、observability。

如果你想**做低代码 agent 平台**：优先研究 **Dify、Open Agent Builder、Flowise、Agno**。重点看：DAG 节点、工具市场、RAG、权限、日志、部署 API、人审节点。

最后一个小提醒：**Roo Code 目前不建议作为新项目底座**。它的 GitHub README 明确写着 Roo Code Extension 已在 2026-05-15 shut down，并建议看社区 fork ZooCode 或 Cline。([GitHub][agent-35])
